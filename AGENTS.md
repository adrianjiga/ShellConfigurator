# AGENTS.md

Interactive Ink (React) TUI that walks users through configuring Starship. Node >=24, ESM.

## Commands

- `npm run dev` — run the wizard via tsx (interactive TUI). **Dangerous**: it runs real system installs (`sudo apt/dnf/pacman/apk`, `chsh`) and writes per-shell configs `~/.config/starship/<shell>.toml` (keeping a `.pre-shell-configurator` copy of each user file it first changes, such as a shared `~/.config/starship.toml`), Nerd Fonts, and shell RC files (`~/.zshrc`, `~/.bashrc`, `~/.config/fish/config.fish`). Never run it to "test" a change on a machine you don't want modified; verify logic via unit tests instead.
- `npm test` / `npm test -- --run <file>` — vitest, tests in `src/__tests__/` mirroring `src/`. Single test: `npx vitest run src/__tests__/generators/starship.test.ts`. `npm run test:coverage` adds the v8 report (thresholds in `vitest.config.ts`). `src/__tests__/helpers/setup.ts` (vitest `setupFiles`) stubs `renderPromptAsync` to the static fallback for every test so no test spawns the real `starship`; a test that needs the real preview opts in with `vi.unmock('../../services/preview.ts')` (see `preview.test.ts`). `vitest.config.ts` sets `FORCE_COLOR=0` for the workers, so an editor's test runner (which forces colour) renders the same plain frames the screen tests assert.
- `npm run lint` (biome over `src`, `scripts` and `vitest.config.ts`; `no-explicit-any` is an error), `npm run format:check` / `npm run format` (biome). Biome config lives in `biome.json`; the linter sidesteps the `typescript` compiler, so TS 7 updates don't break it.
- `npm run build` — `tsc`, emits `dist/`. `npm run typecheck` (`tsconfig.test.json`) type-checks **including** `src/__tests__`, which the build config excludes; run it before pushing. `npm run typecheck:scripts` builds, then type-checks the `scripts/**/*.mjs` smokes against the emitted `dist/` declarations (`tsconfig.scripts.json`). `npm run pack:check` (`scripts/ci/packSmoke.mjs`) packs the tarball and boots `dist/index.js --version` from it.
- CI splits into `.github/workflows/ci.yml` (a `quality-checks` matrix of lint, format:check, typecheck, typecheck:scripts, build and pack:check aggregated by `Quality gate`; a `ci-lint` job running shellcheck, actionlint and zizmor; the `distro-smoke` Docker matrix; and a native `macos-smoke` job) and `.github/workflows/tests.yml` (the v8 coverage gate on Node 24 + 26 Ubuntu plus a Node 24 macOS runner). Both trigger on push to master and PRs to master. Each `distro-smoke` cell (`scripts/ci/distroSmoke.sh` → `distroRunner.sh` in the container) runs `scripts/dockerSmoke.mjs`, then its `wizard-check` smokes against a scratch `$HOME` under `/tmp` (`scripts/ci/smokeHome.mjs` guard): every cell runs `scripts/ci/headlessGenerateSmoke.mjs` (real `generate` via `dist/`, asserts stdout + `-o`/`--export`, parses the TOML, then a real `debug-info` and `debug-info --json`, asserting the sections and that `$HOME` never appears, loads the real `completions bash` into bash and checks what it completes, matches a line of `list fonts`, parses `list presets --json` and `apply --dry-run --json`, checking its `.bashrc` diff and that the dry run left the file alone, then checks `generate --markdown`'s card rebuilds the TOML it shows), every cell but `brew` (a stub binary) runs `scripts/ci/headlessApplySmoke.mjs` (a real `apply --shells bash`, asserting `Verify config` passed, then checks the `WHAT-CHANGED.md` summary it wrote and runs `doctor --timings --json --config` on the config it wrote (tolerating exit 1 from a failing check), then a real `uninstall --yes` that must leave the summary, keep the rc's pre-apply content (when it had no ShellConfigurator block) as its `.pre-shell-configurator` copy and write no `.bak-` file, a no-op second uninstall, a `rollback --list`, a `rollback --yes` that must bring the rc block and config back, and a second `rollback --yes` that must undo the apply, summary included), and only the `script` cell first runs `scripts/ci/wizardSmoke.mjs` (drives the _real_ `App` from `dist/` through the full install flow). `macos-smoke` runs `scripts/ci/macosSmoke.mjs`: `generate`, an `apply --adopt --dry-run`, and a real headless `apply` (brew + Verify config) in a scratch `$HOME`. `.github/workflows/dependabot-automerge.yml` enables auto-merge only for semver-patch bumps of direct dev dependencies, never `typescript` (it compiles the shipped `dist/`), via `dependabot/fetch-metadata`. `.github/workflows/biome-autofix.yml` runs `biome migrate --write`, `biome check --write src` and `npm run format` on Dependabot dependency PRs in a read-only job (so formatter changes in a Biome bump land with the bump), pushes the resulting patch from a separate job, and re-dispatches `ci.yml`/`tests.yml` via `workflow_dispatch` because a `GITHUB_TOKEN` push does not trigger workflows. GitHub Actions are pinned to commit SHAs with `# vX.Y.Z` comments so Dependabot can update them.
- `.npmrc` sets `legacy-peer-deps=true` — required for Ink's peer deps; don't remove. `prepare` runs `npm run build` on every install.

## Repository rules and releases

- `master` is protected by the GitHub ruleset "master protection" (configured on GitHub, not in the repo): PRs only, no force-push/deletion on the branch (tags are unaffected), 0-approval solo merge, and 11 required status checks — Quality gate (the `ci.yml` quality-checks matrix), Shell and workflow lint (`ci-lint`: shellcheck, actionlint, zizmor), Coverage gate (Node 24/26 Ubuntu + Node 24 macOS via `tests.yml`), and the 8 distro-smoke jobs (7 Linux Docker cells over 5 images — `debian:bookworm-slim` backs the apt, brew and script cells — + the native `Distro smoke (macos)`) — with branches tested against latest master (`strict`). CodeQL still scans via a `code_quality` rule (errors only) rather than a required check, because CodeQL contexts don't run on Dependabot PRs.
- Releasing: bump `package.json` + lockfile, push a `v*` tag (it must be on master and match the `package.json` version, or `release.yml` refuses it) → `release.yml` stages to npm via OIDC and creates the GitHub release with the `npm pack` tarball; then approve the staged package with 2FA (`npm stage approve` / npmjs Staged Packages tab).
- The curl installer (`scripts/install.sh`) consumes the GitHub-release tarball, which must stay self-contained: `bundleDependencies` (fflate, ink, ink-select-input, react) keep `node_modules` inside the packed tarball. Verify with `npm run pack:check` (packs, extracts and boots `dist/index.js` from the tar) — a bare `dist/` tarball crashes with `ERR_MODULE_NOT_FOUND`.

## Architecture

- `src/index.tsx` renders `<App/>` (Ink), with `interactive: true` so it draws even with `CI` set, and only on a terminal (`assertWizardTerminal`). It runs `main()` and installs its crash handlers only when it is the file being run (`isEntryPoint`, symlinks resolved), so importing it starts nothing. `src/app.tsx` owns all `WizardState` and the linear step flow (`STEP_ORDER` in `src/types.ts`): welcome → fontcheck → font_select → preset → segments_left → segments_right → style → shells → review → installing → done. Step navigation is the pure `getNextStep`/`getPrevStep` pair in `src/stepMachine.ts`, wrapped by `goNext`/`goBack` in `app.tsx`. The `review` step (between `shells` and `installing`) is a confirmation gate showing the generated per-shell TOML, the rc lines to be appended, and the install plan (`buildTaskList`); it is visited in dry-run mode too (installing is still skipped).
- The `font_select` step is conditionally skipped based on the `NerdFontChoice` union in `nerdFontToInstall` (`{kind:'none'} | {kind:'select'} | {kind:'install',id}`), driven by the single `shouldVisitFontSelect()` predicate (`types.ts`). Task-building uses `fontIdToInstall()` to get the concrete id. There is no sentinel string.
- `character` module is special: never shown as a toggle in `SegmentsScreen`, always appended to `leftModules`, and never placeable on the right (`placedModules` in `config/modules.ts` dedupes left/right for the card, generator and preview; a card with `character` on the right is rejected). `generateToml` always ends the format with `\n$character` and always writes the `[character]` block, regardless of the module lists.
- `starship.ts` deliberately uses `$fill` (inline) instead of `right_format` for right-side modules — `right_format` pins to the cursor line and misaligns two-line prompts. Do not "fix" this; `starship.test.ts` asserts its absence.
- `services/detector.ts` exposes only `*Async` detection functions, so detection does not hold up the Ink render loop (`findStarshipAsync` only checks the script-install bin dir for a binary off PATH); the preview and the Review screen still call `getMissingStarshipPathDir`, whose `command -v` is sync. `scripts/dockerSmoke.mjs` awaits them via top-level `await`. It also detects the terminal (`detectTerminalAsync`) and containers (`detectContainerAsync`: env vars `CODESPACES`/`REMOTE_CONTAINERS`/`DEVCONTAINER`/`CI`/`KUBERNETES_SERVICE_HOST`/`container`, where `false`/`0`/`no` count as unset, then marker files like `/.dockerenv`, `/run/.containerenv`); in a container the Nerd Font and `chsh` tasks are dropped and the wizard does not offer them. `detectRemoteSessionAsync` finds an SSH session or WSL (`remoteSession`, a runtime field); there the font and terminal font steps are dropped too (`fontsElsewhere` in `installTasks.ts` gives the reason the screens show), while `chsh` still runs.
- Install orchestration lives in `services/installTasks.ts` as `runInstallTasks(state, deps, onUpdate, signal?)` with injected deps (`InstallTaskDeps`, real wiring in `DEFAULT_INSTALL_TASK_DEPS`) so it's unit-testable; screens pass real deps, tests pass fakes. The optional `AbortSignal` halts the chain at phase boundaries and marks unrun tasks failed — never silently done. Two post-install phases are guarded by their injected deps too: `Verify config` (runs `starship print-config` on the written configs, resolving a script-install bin dir via `getMissingStarshipPathDir`) and `wireTerminalFont` (`services/terminalFont.ts`, edits alacritty/kitty/ghostty/foot configs; WezTerm's Lua config returns a note instead). A fresh Starship install records its version (`recordStarshipVersion`, in `services/cache.ts`) so the doctor can flag drift.
- Day-2 health lives in `services/doctor.ts` (`runDoctor`, read-only) with its checks under `services/doctor/` (`starshipChecks.ts` incl. `checkVersionDrift` against the recorded starship version, `shellChecks.ts` incl. `checkShellWiring` and `checkRunningShell`, `fontChecks.ts`, the injected `DEFAULT_DOCTOR_DEPS` in `deps.ts`, the types in `types.ts`) and `services/repair.ts` (`runRepair` applies the fixes of failing findings, plus warnings only with `includeWarnings`, then re-runs the doctor; `dryRun` only lists them as planned). Without a card `runDoctor` checks only the installed shells that were set up (`lastRunShells`, `startsStarship` or `hasManagedRcBlock`), so a never-chosen bash is no failure; on macOS Bash fails when its login file does not load `~/.bashrc`. They are wired in headlessly as `doctor` and `doctor --fix` (`--include-warnings`, `--dry-run`, `--yes`, `--json`; config flags without `--state` are ignored with a warning; the old `repair` subcommand is a usage error pointing here); `runRepairCommand` plans with a dry run first, asks through `confirmChanges` like uninstall, runs the fixes inside `captureRun` and records a `repair` history entry; tests drive the real services against faked `exec`/`fs` (`src/__tests__/services/healthIntegration.test.ts`), following the `vi.hoisted` pattern below.
- Teardown lives in `services/uninstall.ts` (`planUninstall` builds read-only steps in reverse install order, `runUninstall` runs them, injected `UninstallDeps`), wired in as the `uninstall` subcommand (`runUninstallCommand` in `index.tsx`). It strips every ShellConfigurator block from an rc via `removeManagedRcBlocks` (keeping a carried PATH line when the user's own init line or fish's `conf.d` init stays) and deletes per-shell configs (`removeShellConfigFile`); a shell's config step is skipped when its rc step failed, and the report points at `rollback` (or, when the run could not be captured, says rollback cannot undo it and names the `<file>.pre-shell-configurator` copies). Starship (`--starship`) and a font (`--font <id>`, names read from its cached archive's headers, else from the `<id>.files` list its install recorded) are opt-in. `plannedStarshipRemoval` only deletes a `~/.local/bin/starship` whose SHA-256 matches what this tool's script install recorded. `plannedStarshipRemoval` only plans a package removal when that package manager owns the binary (pacman `-Qqo`, apk `--who-owns`, or the binary's real path inside `brew --prefix starship`), and the step is held back while `startsStarship` says any shell would still start it. It asks on a terminal and refuses to change anything elsewhere without `--yes`.
- After a real wizard install (`InstallingScreen`, passing `summaryPath` back in `WizardState`) or `apply`, `services/whatChanged.ts` writes `~/.config/starship/WHAT-CHANGED.md` from the results and the files the run changed; it is best-effort (`writeWhatChangedSafely` returns null on failure). It is written from `captureRun`'s `onChanged` step (only for a run that changed files, before its manifest is written, also after a throw), as a captured file marked `rewritable`, so rolling the run back restores the previous summary; a rollback leaves a rewritable file alone without counting it as left only when a later captured run wrote its current content (`laterRunWrites`), so a hand edit still makes it partial. `uninstall` and `rollback` leave it alone. `setup.ts` stubs `writeWhatChangedSafely` so no test writes into the real home (its own tests `vi.unmock` it). `list <presets|modules|fonts> [--json]` (`services/listings.ts`, `runListCommand` in `index.tsx`) and `apply --dry-run --json` (`dryRunPlan` in `applyReport.ts`; flags become a state card in `stateFlags.ts`, `--import-url` is fetched in `importConfig.ts`, and `headless.ts` keeps `runGenerate`/`runApply`) are the scripting surface. `doctor --timings` (`timingSource`/`timeSource` in `index.tsx`, `timePrompt` in `services/starshipProbe.ts`) reads the config to time first (an unreadable `--config` is a usage error before any check runs), then runs the health check and times the config Starship loads in the current folder (or `--config <file>`) with `starship timings` and suggests fixes, as a `timings` field with `--json`; a timing failure prints `Could not time the prompt: …` and exits 1, and `--timings` with `--fix` is refused; `explainPromptAsync` there runs `starship explain` for the Review step's `e` section (stubbed in `setup.ts`). `generate --markdown` (`runMarkdownCommand`; `-o` writes the file, and `--shells`, `--set-default`, `--skip-starship`, `--export` and `--dry-run` are refused with it) and the Done screen's `s` render the prompt as Markdown with a card that rebuilds it (`services/share.ts`); the card drops this machine's shells, font install and default shell. Probes that run Starship pass the folder as both `--path` and `PWD`, since Starship takes the directory from `PWD`. A dry run and the Review screen diff the configs and rc files a run would write against disk (`plannedFileChanges` in `services/fileDiff.ts`); the rc side comes from `appliedRcContent`/`resetRcContent` in `rcPlan.ts`, the same pure planners `applyShellConfig`/`resetSharedShellConfig` write from, so a change to the rc logic belongs there. Tests that point `HOME` at a scratch folder use `vi.stubEnv` (or set `process.env.HOME` in place), and tests that save and restore the environment use `restoreEnv` (`src/__tests__/helpers/env.ts`): replacing `process.env` with a copy detaches it from the real environment, and `os.homedir()` then keeps returning the old home.
- `completions <bash|zsh|fish>` (`services/completions.ts`) generates its scripts from `services/cliSurface.ts`, which describes every subcommand, its flags and their values. Adding or renaming a flag in `args.ts` means describing it in `cliSurface.ts` too; `completions.test.ts` fails otherwise (it compares against the parser's exported `KNOWN_FLAGS`). `SUBCOMMAND_INFO` is also what `refuseUnusedFlags` checks every subcommand against, so a flag a subcommand would ignore is a usage error (doctor still only warns about config flags without `--state`). A flag or subcommand that no longer exists goes in `RETIRED_FLAGS` or `RETIRED_SUBCOMMANDS` in `args.ts` with what to use instead (`--undo`/`--restore` → `rollback`, `--list-*` → `list`, `repair` → `doctor --fix`, `share` → `generate --markdown`, `timings` → `doctor --timings`), so it is a usage error (exit 2) naming the replacement. `parseState` refuses a card key it does not know. The tests run the scripts through real `bash`, and `zsh`/`fish` where installed. `completions` and `list` are the only subcommands with a positional argument (`CliFlags.argument`). The zsh script's function is named `_shell-configurator`, after the file zsh autoloads it from, so the first Tab completes; bash splits file candidates on newlines only (`local IFS`), since macOS ships bash 3.2 without `mapfile`.
- `debug-info` (`services/debugInfo.ts`, `runDebugInfoCommand` in `index.tsx`) is read-only: `collectDebugInfo` gathers detection, Starship, per-shell facts (`startsStarship`, `hasManagedRcBlock`), PATH, the last history record and `runDoctor(null)` through injected `DebugInfoDeps`; `formatDebugInfo` renders Markdown. Both outputs pass through `redactPersonal` (in `services/redact.ts`: `redactHome` turns the home folder into `~`, matched only between characters that cannot continue a path name, and `redactUser` turns the user name into `<user>` after a `Users/` or `home/` folder), as do `generate --markdown` and crash output; the summary and the Review screen use `redactHome` alone. `recordRun` stores commands through `redactUrls` (URL credentials, queries and fragments dropped), and `rollback --list` shows them that way too.
- Rollback is the only undo (ADR 0006; there are no `.bak-*` files and no `--restore`): wizard installs (`InstallingScreen`, passing `runId` back in `WizardState`, so the Done screen can point at `shell-configurator rollback`), headless `apply`, `doctor --fix`, `uninstall` and `rollback` itself wrap their work in `captureRun(trackedFiles(), …)` (`services/runCapture.ts`), which copies every file they may change into `<stateDir>/runs/<runId>/` and keeps a manifest of those they did change (`before` copy, `after` hash); `recordRun` stores the `runId` (and a rollback's `rollbackOf`). `services/rollback.ts` lists runs from history (`listRollbackRuns`, newest first; a run is rolled back while an un-undone rollback of it exists), plans per-file restores/deletes (exact bytes and the captured mode) and skips any file whose hash no longer matches `after`, re-checking right before each change; a rollback that left a change in place is recorded `partial` and does not count as undoing the run, and one whose files were all back already is recorded without asking, so the run counts as rolled back. A run that throws inside `captureRun` rejects with `CapturedRunError` (carrying its `runId`), which the wizard and `apply` still record. Run folders are created exclusively (`mkdir` without `recursive`), removed when a capture fails partway, and pruned to the newest 50 (`pruneRuns`). A capture writes `pending.json` (its pid, the captured files and the `record` option) when it starts and removes it with the manifest; `recoverInterruptedRuns`, run before every capture and by `rollback`, finishes the capture of a run whose process is gone (claiming it first by renaming `pending.json` to `pending.json.<pid>`, so two processes never recover the same run) and records it `interrupted` (a rollback also `partial`), so a killed run stays undoable and history keeps its order. Headless `apply` cancels its steps on SIGINT/SIGTERM/SIGHUP through `cancelOnSignals` (`services/cancel.ts`; a second signal exits at once) and exits with 128 + the signal number; the wizard's `InstallingScreen` cancels on the same three. A file the run left unreadable stays in the manifest as `UNREADABLE_AFTER`; a rollback with no `runId` (its own capture failed) still counts as undoing its `rollbackOf`. Uninstall's Starship step re-checks `startsStarship` just before deleting, and the uninstall report says rollback cannot reinstall a removed Starship or font. The `rollback` subcommand (`runRollbackCommand`, `--list`, `--run <id>`, `--yes`, `--dry-run`, `--json`) shares `confirmChanges` with uninstall. Capture is best-effort and must never fail a run; `captureRun` tells `run` when it could not start the capture, and uninstall then leaves the per-shell configs in place (`keepConfigs`); it also returns `uncaptured`, true when the run could not be recorded at either end, which is what uninstall's "could not be recorded" warning checks (a null `runId` alone may just mean nothing changed). `src/__tests__/helpers/setup.ts` stubs `captureRun` so no test copies the real rc files; tests of the capture itself opt in with `vi.unmock('../../services/runCapture.ts')`.
- Generators/services (`generators/`, `services/`, `config/`) are unit-tested; key screen key-handling is covered via `ink-testing-library` (`src/__tests__/screens/`), and remaining edge cases by a manual test plan the maintainer keeps locally (not in the repo).
- Docs live in `docs/` (Architecture, Technical-Design, API-Interface-Design, UI-UX-Design, generated-config, troubleshooting, `decisions/` ADRs) and are a good source for wiring details.

## Conventions

- Always use conventional commit messages (e.g. `feat:`, `fix:`, `ci:`, `docs:`, `chore:`).
- Never commit or push directly to `master`/`main` — every change goes through a feature branch and a PR.
- Every PR description has these sections: **Summary**, **Why**, **What Changed**.
- ESM: relative imports name the real source file (e.g. `from './types.ts'`, `from './app.tsx'`). `rewriteRelativeImportExtensions` rewrites them to `.js` on emit, so `dist/` stays valid for Node's ESM resolver. Never write `.js` in source.
- pacman installs with `-S --needed` and never `-Syu`: a full system upgrade is the user's call; a failed install says to run `sudo pacman -Syu` first.
- Package manager detection order matters and is asserted in tests: brew → pacman → os-release distro id → apt-get/dnf/apk binary → `script`. The `distro-smoke` matrix (with Alpine) guards it.
- Binary checks live in `services/exec.ts` and use `sh -c 'command -v "$1"' sh <cmd>`, never `which` — `which` is absent on minimal/Fedora/Alpine images, and passing the name as `$1` keeps it out of the script text. The CI `distro-smoke` job guards it.
- The `distro-smoke` containers run `scripts/ci/distroSetup.sh` right after the per-cell setup hook (`distroRunner.sh` runs the hook first, since it installs bash). `distroSetup.sh` upgrades to a pinned Node 24 tarball when the distro ships an older node (debian/ubuntu ship 18) so the run uses the supported engine floor. Don't remove or inline it.
- All install commands go through `runCommand` in `services/exec.ts`: async `spawn`, never `spawnSync`, and it suspends the Ink UI (`services/tty.ts`) for the child's lifetime so sudo prompts are not painted over. `suspendUi` also stops Node's read on the terminal handle (a removed input listener does not), and `resumeUi` starts it again, so a typed password reaches the child; no `useInput` may stay active during the install (`app.tsx`'s is off on that step).
- `detector.test.ts` shows the required mocking pattern: `vi.hoisted` mocks plus a `Symbol.for('nodejs.util.promisify.custom')` stub so promisified `execFile` resolves correctly. Follow it when adding detection tests.
- The rc code lives in `src/generators/`: `shellRc.ts` writes (apply, reset, remove, config files), `rcPlan.ts` holds the pure planners, `rcLines.ts` the markers and line rules, `rcInit.ts` init detection (`initReachable`, `startsStarship`, `keepsOwnConfig`), `bashLogin.ts` the macOS login file, `fileWrite.ts` `writeFileAtomic` and `keepOriginal`, `configPaths.ts` the config paths. `applyShellConfig`/`resetSharedShellConfig` are idempotent. Whether a shell already starts Starship is decided by `initReachable`, which also follows `source`/`.` lines (with `~` and `$VAR` expanded) up to three files deep, since setups like Omarchy run `starship init` from a file `~/.bashrc` sources; such a shell gets no second init line. A managed block runs from its marker to its init line, holds at most one `STARSHIP_CONFIG` line, and counts a PATH line as its own only when it adds `~/.local/bin` the way the tool writes it (today's or the pre-1.3.0 form), so a user's own export, init or PATH line right under a block is never taken for part of it. `applyShellConfig` keeps per-shell and adopt mode mutually exclusive: before writing it removes the stale unset guard and the opposite mode's block/export (only the two exact `# Added by ShellConfigurator` markers count as managed), carries a removed block's PATH line over, and inserts above an existing init line, or above the `source` line that reaches one (as do the unset guard and a PATH line uninstall keeps). `resetSharedShellConfig` removes a stale per-shell block from an earlier run (keeping its PATH line and init) and adds the unset guard above the init line. It only runs for unselected shells without a working setup of their own: `plannedResetShells` and the run skip a shell whose rc exports `STARSHIP_CONFIG` to its existing per-shell config (`keepsOwnConfig`), since that export already overrides a leaked one; `keepsOwnConfig` accepts the export however an earlier version quoted it; `shellsToGuard` is the one place both use. A shell whose own, hand-written line sets `STARSHIP_CONFIG` (`export`, `typeset -x`, `declare -x`, fish `set -x`) in its rc, a file the rc sources, or another startup file (`.zshenv`, `.zprofile`, `.bash_profile`, `.bash_login`, `.profile`) keeps it and gets no guard (a stale guard is removed). The two are mutually exclusive: an apply after a reset drops the guard, and a reset after an apply drops the per-shell export. Keep that behavior. On macOS `applyShellConfig('bash')` also makes the Bash login file (`bashLoginFile`: the first of `.bash_profile`, `.bash_login`, `.profile` that exists, else a new `.bash_profile`) load `~/.bashrc`, since macOS terminals start login shells; the line is guarded by `$BASH_VERSION`, a failed login-file write is only a note on the Bash step, `uninstall` takes it back out in its own `Bash login file` step (`removeBashLoginBlock`, planned whenever a login file holds it, even with no block in `.bashrc`), the dry-run diff shows it and `trackedFiles` captures all three. Tests that touch Bash pin the platform with `stubPlatform` (`src/__tests__/helpers/platform.ts`). rc/config writes go through `writeFileAtomic` (temp file + rename, writes through symlinks, keeps permissions, refuses read-only files). Before the tool first changes a user file (rc files on apply and reset, the Bash login file, the shared `starship.toml` in `writeSharedConfig`, terminal configs in `terminalFont.ts`), `keepOriginal` copies it to `<file>.pre-shell-configurator` once and never again (skipped when the file already holds a `# Added by ShellConfigurator` block or the `# Generated by ShellConfigurator` header, or the copy exists); it is best-effort, returning a note the step reports instead of failing it. Per-shell and shared config writes call it only when the content changes, and uninstall calls it before deleting a per-shell config, so a hand-written one is kept once; the generated-header skip applies only with `toolOwned` (the per-shell configs), so a shared config made with `generate -o` still gets its copy. `trackedFiles` includes each file's `.pre-shell-configurator` path, so rolling back the run that made a copy deletes it, but only once the file it belongs to is back as it was (`keepCopiesOfFilesLeft` in `rollback.ts`).
