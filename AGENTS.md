# AGENTS.md

Interactive Ink (React) TUI that walks users through configuring Starship. Node >=24, ESM.

## Commands

- `npm run dev` — run the wizard via tsx (interactive TUI). **Dangerous**: it runs real system installs (`sudo apt/dnf/pacman/apk`, `chsh`) and writes per-shell configs `~/.config/starship/<shell>.toml` (backing up a shared `~/.config/starship.toml`), Nerd Fonts, and shell RC files (`~/.zshrc`, `~/.bashrc`, `~/.config/fish/config.fish`). Never run it to "test" a change on a machine you don't want modified; verify logic via unit tests instead.
- `npm test` / `npm test -- --run <file>` — vitest, tests in `src/__tests__/` mirroring `src/`. Single test: `npx vitest run src/__tests__/generators/starship.test.ts`. `npm run test:coverage` adds the v8 report (thresholds in `vitest.config.ts`). `src/__tests__/helpers/setup.ts` (vitest `setupFiles`) stubs `renderPromptAsync` to the static fallback for every test so no test spawns the real `starship`; a test that needs the real preview opts in with `vi.unmock('../../services/preview.ts')` (see `preview.test.ts`). `vitest.config.ts` sets `FORCE_COLOR=0` for the workers, so an editor's test runner (which forces colour) renders the same plain frames the screen tests assert.
- `npm run lint` (biome over `src`, `scripts` and `vitest.config.ts`; `no-explicit-any` is an error), `npm run format:check` / `npm run format` (biome). Biome config lives in `biome.json`; the linter sidesteps the `typescript` compiler, so TS 7 updates don't break it.
- `npm run build` — `tsc`, emits `dist/`. `npm run typecheck` (`tsconfig.test.json`) type-checks **including** `src/__tests__`, which the build config excludes; run it before pushing. `npm run typecheck:scripts` builds, then type-checks the `scripts/**/*.mjs` smokes against the emitted `dist/` declarations (`tsconfig.scripts.json`). `npm run pack:check` (`scripts/ci/packSmoke.mjs`) packs the tarball and boots `dist/index.js --version` from it.
- CI splits into `.github/workflows/ci.yml` (a `quality-checks` matrix of lint, format:check, typecheck, typecheck:scripts, build and pack:check aggregated by `Quality gate`; a `ci-lint` job running shellcheck, actionlint and zizmor; the `distro-smoke` Docker matrix; and a native `macos-smoke` job) and `.github/workflows/tests.yml` (the v8 coverage gate on Node 24 + 26 Ubuntu plus a Node 24 macOS runner). Both trigger on push to master and PRs to master. Each `distro-smoke` cell (`scripts/ci/distroSmoke.sh` → `distroRunner.sh` in the container) runs `scripts/dockerSmoke.mjs`, then its `wizard-check` smokes against a scratch `$HOME` under `/tmp` (`scripts/ci/smokeHome.mjs` guard): every cell runs `scripts/ci/headlessGenerateSmoke.mjs` (real `generate` via `dist/`, asserts stdout + `-o`/`--export`, parses the TOML, then a real `debug-info` and `debug-info --json`, asserting the sections and that `$HOME` never appears, loads the real `completions bash` into bash and checks what it completes, and parses `--list-presets --json`, `--list-fonts` and `apply --dry-run --json`, checking its `.bashrc` diff and that the dry run left the file alone), every cell but `brew` (a stub binary) runs `scripts/ci/headlessApplySmoke.mjs` (a real `apply --shells bash`, asserting `Verify config` passed, then checks the `WHAT-CHANGED.md` summary it wrote, then a real `uninstall --yes`, a no-op second uninstall, a `rollback --list`, a `rollback --yes` that must bring the rc block and config back, and a second `rollback --yes` that must undo the apply), and only the `script` cell first runs `scripts/ci/wizardSmoke.mjs` (drives the _real_ `App` from `dist/` through the full install flow). `macos-smoke` runs `scripts/ci/macosSmoke.mjs`: `generate`, an `apply --adopt --dry-run`, and a real headless `apply` (brew + Verify config) in a scratch `$HOME`. `.github/workflows/dependabot-automerge.yml` enables auto-merge only for semver-patch bumps of direct dev dependencies, never `typescript` (it compiles the shipped `dist/`), via `dependabot/fetch-metadata`. `.github/workflows/biome-autofix.yml` runs `biome migrate --write`, `biome check --write src` and `npm run format` on Dependabot dependency PRs in a read-only job (so formatter changes in a Biome bump land with the bump), pushes the resulting patch from a separate job, and re-dispatches `ci.yml`/`tests.yml` via `workflow_dispatch` because a `GITHUB_TOKEN` push does not trigger workflows. GitHub Actions are pinned to commit SHAs with `# vX.Y.Z` comments so Dependabot can update them.
- `.npmrc` sets `legacy-peer-deps=true` — required for Ink's peer deps; don't remove. `prepare` runs `npm run build` on every install.

## Repository rules and releases

- `master` is protected by the GitHub ruleset "master protection" (configured on GitHub, not in the repo): PRs only, no force-push/deletion on the branch (tags are unaffected), 0-approval solo merge, and 10 required status checks — Quality gate (the `ci.yml` quality-checks matrix), Coverage gate (Node 24/26 Ubuntu + Node 24 macOS via `tests.yml`), and the 8 distro-smoke jobs (7 Linux Docker cells over 5 images — `debian:bookworm-slim` backs the apt, brew and script cells — + the native `Distro smoke (macos)`) — with branches tested against latest master (`strict`). CodeQL still scans via a `code_quality` rule (errors only) rather than a required check, because CodeQL contexts don't run on Dependabot PRs.
- Releasing: bump `package.json` + lockfile, push a `v*` tag (it must be on master and match the `package.json` version, or `release.yml` refuses it) → `release.yml` stages to npm via OIDC and creates the GitHub release with the `npm pack` tarball; then approve the staged package with 2FA (`npm stage approve` / npmjs Staged Packages tab).
- The curl installer (`scripts/install.sh`) consumes the GitHub-release tarball, which must stay self-contained: `bundledDependencies` (fflate, ink, ink-select-input, react) keep `node_modules` inside the packed tarball. Verify with `npm run pack:check` (packs, extracts and boots `dist/index.js` from the tar) — a bare `dist/` tarball crashes with `ERR_MODULE_NOT_FOUND`.

## Architecture

- `src/index.tsx` renders `<App/>` (Ink). `src/app.tsx` owns all `WizardState` and the linear step flow (`STEP_ORDER` in `src/types.ts`): welcome → fontcheck → font_select → preset → segments_left → segments_right → style → shells → review → installing → done. Step navigation is the pure `getNextStep`/`getPrevStep` pair in `src/stepMachine.ts`, wrapped by `goNext`/`goBack` in `app.tsx`. The `review` step (between `shells` and `installing`) is a confirmation gate showing the generated per-shell TOML, the rc lines to be appended, and the install plan (`buildTaskList`); it is visited in dry-run mode too (installing is still skipped).
- The `font_select` step is conditionally skipped based on the `NerdFontChoice` union in `nerdFontToInstall` (`{kind:'none'} | {kind:'select'} | {kind:'install',id}`), driven by the single `shouldVisitFontSelect()` predicate (`types.ts`). Task-building uses `fontIdToInstall()` to get the concrete id. There is no sentinel string.
- `character` module is special: never shown as a toggle in `SegmentsScreen`, always appended to `leftModules`, and never placeable on the right (`placedModules` in `config/modules.ts` dedupes left/right for the card, generator and preview; a card with `character` on the right is rejected). `generateToml` always ends the format with `\n$character` and always writes the `[character]` block, regardless of the module lists.
- `starship.ts` deliberately uses `$fill` (inline) instead of `right_format` for right-side modules — `right_format` pins to the cursor line and misaligns two-line prompts. Do not "fix" this; `starship.test.ts` asserts its absence.
- `services/detector.ts` exposes only `*Async` detection functions, so nothing blocks the Ink render loop. `scripts/dockerSmoke.mjs` awaits them via top-level `await`. It also detects the terminal (`detectTerminalAsync`) and containers (`detectContainerAsync`: env vars `CODESPACES`/`REMOTE_CONTAINERS`/`DEVCONTAINER`/`CI`/`KUBERNETES_SERVICE_HOST`/`container`, where `false`/`0`/`no` count as unset, then marker files like `/.dockerenv`, `/run/.containerenv`); in a container the Nerd Font and `chsh` tasks are dropped and the wizard does not offer them.
- Install orchestration lives in `services/installTasks.ts` as `runInstallTasks(state, deps, onUpdate, signal?)` with injected deps (`InstallTaskDeps`, real wiring in `DEFAULT_INSTALL_TASK_DEPS`) so it's unit-testable; screens pass real deps, tests pass fakes. The optional `AbortSignal` halts the chain at phase boundaries and marks unrun tasks failed — never silently done. Two post-install phases are guarded by their injected deps too: `Verify config` (runs `starship print-config` on the written configs, resolving a script-install bin dir via `getMissingStarshipPathDir`) and `wireTerminalFont` (`services/terminalFont.ts`, edits alacritty/kitty/ghostty/foot configs; WezTerm's Lua config returns a note instead). A fresh Starship install records its version (`recordStarshipVersion`, in `services/cache.ts`) so the doctor can flag drift.
- Day-2 health lives in `services/doctor.ts` (`runDoctor`, read-only, `checkVersionDrift` against the recorded starship version + `checkRunningShell`) and `services/repair.ts` (`runRepair` applies the fixes of failing findings, plus warnings only with `includeWarnings`, then re-runs the doctor; `dryRun` only lists them as planned). They are wired in headlessly as `doctor` (`--fix` = repair) and `repair` subcommands (`--include-warnings`, `--dry-run`, `--json`; config flags without `--state` are ignored with a warning); tests drive the real services against faked `exec`/`fs` (`src/__tests__/services/healthIntegration.test.ts`), following the `vi.hoisted` pattern below.
- Teardown lives in `services/uninstall.ts` (`planUninstall` builds read-only steps in reverse install order, `runUninstall` runs them, injected `UninstallDeps`), wired in as the `uninstall` subcommand (`runUninstallCommand` in `index.tsx`). It strips every ShellConfigurator block from an rc via `removeManagedRcBlocks` (backing the rc up, keeping a carried PATH line when the user's own init line or fish's `conf.d` init stays) and renames per-shell configs to `.bak-*` (`removeShellConfigFile`); a shell's config step is skipped when its rc step failed, and the report points at `rollback` (or, when the run could not be captured, ends with the `cp` commands that copy each backup back; never `--restore`, which also rolls the shared config back). Starship (`--starship`) and a font (`--font <id>`, names read from its cached archive's headers) are opt-in. `plannedStarshipRemoval` only plans a package removal when that package manager owns the binary (pacman `-Qqo`, apk `--who-owns`, or the binary's real path inside `brew --prefix starship`), and the step is held back while `startsStarship` says any shell would still start it. It asks on a terminal and refuses to change anything elsewhere without `--yes`.
- After a real wizard install (`InstallingScreen`, passing `summaryPath` back in `WizardState`) or `apply`, `services/whatChanged.ts` writes `~/.config/starship/WHAT-CHANGED.md` from the results and the run's manifest; it is best-effort (`writeWhatChangedSafely` returns null on failure) and `setup.ts` stubs it so no test writes into the real home (its own tests `vi.unmock` it). `--list-presets`/`--list-modules`/`--list-fonts` (`services/listings.ts`, handled in `runGlobalFlags`) and `apply --dry-run --json` (`dryRunPlan` in `headless.ts`) are the scripting surface. A dry run and the Review screen diff the configs and rc files a run would write against disk (`plannedFileChanges` in `services/fileDiff.ts`); the rc side comes from `appliedRcContent`/`resetRcContent` in `shellRc.ts`, the same pure planners `applyShellConfig`/`resetSharedShellConfig` write from, so a change to the rc logic belongs there. Tests that point `HOME` at a scratch folder use `vi.stubEnv` (or set `process.env.HOME` in place): replacing `process.env` with a copy detaches it from the real environment, and `os.homedir()` then keeps returning the old home.
- `completions <bash|zsh|fish>` (`services/completions.ts`) generates its scripts from `services/cliSurface.ts`, which describes every subcommand, its flags and their values. Adding or renaming a flag in `args.ts` means describing it in `cliSurface.ts` too; `completions.test.ts` fails otherwise (it compares against the parser's exported `KNOWN_FLAGS`). The tests run the scripts through real `bash`, and `zsh`/`fish` where installed. `completions` is the only subcommand with a positional argument (`completionShell`). The zsh script's function is named `_shell-configurator`, after the file zsh autoloads it from, so the first Tab completes; bash splits file candidates on newlines only (`local IFS`), since macOS ships bash 3.2 without `mapfile`.
- `debug-info` (`services/debugInfo.ts`, `runDebugInfoCommand` in `index.tsx`) is read-only: `collectDebugInfo` gathers detection, Starship, per-shell facts (`startsStarship`, `hasManagedRcBlock`), PATH, the last history record and `runDoctor(null)` through injected `DebugInfoDeps`; `formatDebugInfo` renders Markdown. Both outputs pass through `redactHome` (home → `~`), and the recorded command through `redactUrls` (URL credentials, queries and fragments dropped), since the report is meant to be pasted into a public issue.
- Rollback: wizard installs (`InstallingScreen`, passing `runId` back in `WizardState`), headless `apply`, `uninstall` and `rollback` itself wrap their work in `captureRun(trackedFiles(), …)` (`services/runCapture.ts`), which copies every file they may change into `<stateDir>/runs/<runId>/` and keeps a manifest of those they did change (`before` copy, `after` hash); `recordRun` stores the `runId` (and a rollback's `rollbackOf`). `services/rollback.ts` lists runs from history (`listRollbackRuns`, newest first; a run is rolled back while an un-undone rollback of it exists), plans per-file restores/deletes (exact bytes and the captured mode) and skips any file whose hash no longer matches `after`, re-checking right before each change; a rollback that left a change in place is recorded `partial` and does not count as undoing the run. A run that throws inside `captureRun` rejects with `CapturedRunError` (carrying its `runId`), which the wizard and `apply` still record. Run folders are created exclusively (`mkdir` without `recursive`), removed when a capture fails partway, and pruned to the newest 50 (`pruneRuns`). A file the run left unreadable stays in the manifest as `UNREADABLE_AFTER`; a rollback with no `runId` (its own capture failed) still counts as undoing its `rollbackOf`. Uninstall's Starship step re-checks `startsStarship` just before deleting, and the uninstall report says rollback cannot reinstall a removed Starship or font. The `rollback` subcommand (`runRollbackCommand`, `--list`, `--run <id>`, `--yes`, `--dry-run`, `--json`) shares `confirmChanges` with uninstall. Capture is best-effort and must never fail a run. `src/__tests__/helpers/setup.ts` stubs `captureRun` so no test copies the real rc files; tests of the capture itself opt in with `vi.unmock('../../services/runCapture.ts')`.
- Generators/services (`generators/`, `services/`, `config/`) are unit-tested; key screen key-handling is covered via `ink-testing-library` (`src/__tests__/screens/`), and remaining edge cases by a manual test plan the maintainer keeps locally (not in the repo).
- Docs live in `docs/` (Architecture, Technical-Design, API-Interface-Design, UI-UX-Design, generated-config, troubleshooting, `decisions/` ADRs) and are a good source for wiring details.

## Conventions

- Always use conventional commit messages (e.g. `feat:`, `fix:`, `ci:`, `docs:`, `chore:`).
- Never commit or push directly to `master`/`main` — every change goes through a feature branch and a PR.
- Every PR description has these sections: **Summary**, **Why**, **What Changed**.
- ESM: relative imports name the real source file (e.g. `from './types.ts'`, `from './app.tsx'`). `rewriteRelativeImportExtensions` rewrites them to `.js` on emit, so `dist/` stays valid for Node's ESM resolver. Never write `.js` in source.
- Package manager detection order matters and is asserted in tests: brew → pacman → os-release distro id → apt-get/dnf/apk binary → `script`. The `distro-smoke` matrix (with Alpine) guards it.
- Binary checks live in `services/exec.ts` and use `sh -c 'command -v "$1"' sh <cmd>`, never `which` — `which` is absent on minimal/Fedora/Alpine images, and passing the name as `$1` keeps it out of the script text. The CI `distro-smoke` job guards it.
- The `distro-smoke` containers run `scripts/ci/distroSetup.sh` first, which upgrades to a pinned Node 24 tarball when the distro ships an older node (debian/ubuntu ship 18) so the run uses the supported engine floor. Don't remove or inline it.
- All install commands go through `runCommand` in `services/exec.ts`: async `spawn`, never `spawnSync`, and it suspends the Ink UI (`services/tty.ts`) for the child's lifetime so sudo prompts are not painted over.
- `detector.test.ts` shows the required mocking pattern: `vi.hoisted` mocks plus a `Symbol.for('nodejs.util.promisify.custom')` stub so promisified `execFile` resolves correctly. Follow it when adding detection tests.
- `shellRc.ts` `applyShellConfig`/`resetSharedShellConfig` are idempotent. `applyShellConfig` keeps per-shell and adopt mode mutually exclusive: before writing it removes the stale unset guard and the opposite mode's block/export (only the two exact `# Added by ShellConfigurator` markers count as managed), carries a removed block's PATH line over, and inserts above an existing init line. `resetSharedShellConfig` removes a stale per-shell block from an earlier run (keeping its PATH line and init) and adds the unset guard above the init line; a shell whose own, hand-written line sets `STARSHIP_CONFIG` keeps it and gets no guard (a stale guard is removed). The two are mutually exclusive: an apply after a reset drops the guard, and a reset after an apply drops the per-shell export. Keep that behavior. rc/config writes go through `writeFileAtomic` (temp file + rename, writes through symlinks, keeps permissions, refuses read-only files).
