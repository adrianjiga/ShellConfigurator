# Technical Design

## TOML Generator Pipeline

**File**: `src/generators/starship.ts`

The generator takes a `WizardState` and produces a complete `starship.toml` string. The pipeline has three stages.

### Stage 1: Format String Construction

`buildFormatString(modules)` converts a module list into a Starship format string:

```
['directory', 'git_branch', 'git_status'] → '$directory$git_branch$git_status'
```

`buildFormatString` only joins what it is given: `character` is filtered out of the left/right lists before it is called, because `$character` gets special placement after the line break.

### Stage 2: Layout Assembly

`generateToml()` assembles the final `format` value using `$fill` for right-alignment:

```
$directory$git_branch$git_status  $fill  $cmd_duration$time  \n  $character
├── left modules ──────────────┘  │      ├── right modules ─┘   └── prompt line
                                  │
                            fills remaining space
```

This produces a two-line prompt:

```
Line 1: [left info]                          [right info]
Line 2: ❯ _
```

**Why `$fill` instead of `right_format`**: Starship's `right_format` maps to the shell's native RPROMPT, which renders on the cursor line (line 2). This causes right-side modules to appear on a different line than the info modules. `$fill` keeps everything in a single `format` string, avoiding shell-dependent RPROMPT behavior.

### Stage 3: Module Block Generation

`moduleBlock(id, ctx)` produces the TOML `[section]` for each module. The generator
composes `style` and `format` itself from the module's `content` and its palette
colour; each module supplies only its remaining keys via `settings`, so powerline is
a one-place change rather than a per-module one. Blocks adapt to three state values:

- **`hasNerdFont`**: switches between icon symbols and text fallbacks
- **`palette`**: every module is styled with the palette colour of the same name, so
  the generated config refers to colours by name and carries a `[palettes.<id>]` table
- **`powerline`**: wraps each module's content in separator glyphs and swaps its style
  for an `fg:fg bg:<module>` pair, so segments render as interlocking coloured blocks.
  Requires `hasNerdFont`; without it the plain layout is generated instead

Example output for `git_branch` with a Nerd Font, on the default palette:

```toml
[git_branch]
style  = "bold git_branch"
symbol = " "
```

The same module under a powerline prompt, after `directory`. Each module opens
with its own leading separator styled with starship's `prev_bg`, so a module that
collapses takes its separator with it:

```toml
[git_branch]
style  = "bold fg:fg bg:git_branch"
format = "([](fg:prev_bg bg:git_branch)[ $symbol$branch ]($style))"
symbol = " "
```

The surrounding `(…)` is a starship conditional group: it is dropped when every
variable inside is empty, so a module with nothing to show collapses instead of
leaving an empty coloured block and a stray separator in the prompt.

### Dollar Sign Escaping

The dollar character symbol requires two layers of escaping:

1. **Starship level**: `$` is the variable interpolation prefix. A literal `$` must be `\$`.
2. **TOML level**: `\$` is not a valid escape in double-quoted TOML strings. The value must use TOML literal strings (single quotes) so the backslash passes through.

Result in generated TOML:

```toml
success_symbol = '[\$](bold ok)'
```

### Fill Block Generation

When `rightModules` is non-empty, the generator emits a `[fill]` block with an invisible space symbol:

```toml
[fill]
symbol = " "
```

This prevents Starship's default fill behavior (visible dots on light terminals) while keeping left and right modules properly separated.

### Final Output Structure

The top-level keys come first, then the module blocks (left, then right), the
`[character]` block, `[fill]` when there are right-side modules, and finally the
`[palettes.<id>]` table. The default state with `cmd_duration` on the right:

```toml
# Generated by ShellConfigurator
# https://github.com/adrianjiga/ShellConfigurator

format              = "$directory$git_branch$git_status$fill$cmd_duration\n$character"
continuation_prompt = "[∙](bright-black) "
add_newline         = true
palette             = "default"

[directory]
style  = "bold directory"
truncation_length = 3
truncate_to_repo  = true

[git_branch]
style  = "bold git_branch"
symbol = ""

[git_status]
style  = "bold git_status"
ahead     = "⇡${count}"
behind    = "⇣${count}"
diverged  = "⇕⇡${ahead_count}⇣${behind_count}"
modified  = "!${count}"
staged    = "+${count}"
untracked = "?${count}"
deleted   = "-${count}"

[cmd_duration]
style  = "bold cmd_duration"

[character]
success_symbol = '[❯](bold ok)'
error_symbol   = '[❯](bold err)'

[fill]
symbol = " "

[palettes.default]
fg             = "black"
ok             = "green"
err            = "red"
username       = "yellow"
...
```

Styled module blocks reference colours by _name_ (`bold directory`) through the
generated `[palettes.<id>]` table rather than by value, so the whole theme can be
retuned in one place.

## Shell RC Generator

**File**: `src/generators/shellRc.ts`

### Per-Shell Config Writing

`writeShellConfig(toml, shellId)` writes the generated TOML to `~/.config/starship/<shell>.toml`
(`$XDG_CONFIG_HOME` honoured when set):

1. Ensures the per-shell config directory exists
2. Backs up any existing per-shell config to `<shell>.toml.bak-<timestamp>` — overwriting is the one irreversible step in the wizard
3. Writes the new file

Every config and rc write (per-shell, shared, and rc appends) goes through a
temp-file-and-rename in the same directory, so a crash or interrupted run can
never leave a half-written config or rc file.

Normal per-shell setup leaves the shared `~/.config/starship.toml` untouched, so a shell bootstrapped globally (or another tool) keeps working. Adopt mode is the explicit exception described below.

**Adopt mode** (`keepExistingConfig`, set by `apply --adopt`/`--import-url`) is the exception to both of the above. No per-shell files are written at all; instead:

- If `sharedConfigToml` is set (the config was fetched via `--import-url`), `writeSharedConfig(toml)` writes it to the shared path, backing up anything already there (`starship.toml.bak-<timestamp>`).
- Otherwise the existing shared config is left untouched and merely snapshotted via `backupSharedConfig()` so a re-run can restore it.
- Every selected shell is then wired to read that shared file.

### Shell Init Line Injection

`applyShellConfig(shellId)` appends the Starship init line to the shell's RC file together with a
`STARSHIP_CONFIG` export that points at that shell's per-shell config, so each shell renders its own prompt:

```
# Added by ShellConfigurator
export STARSHIP_CONFIG="/home/u/.config/starship/zsh.toml"
eval "$(starship init zsh)"
```

Fish uses `set -gx STARSHIP_CONFIG ...`; nushell and PowerShell have `rcFile: null` and return their
manual note instead.

**Pipeline**:

1. Look up shell definition via `getShell(id)`
2. If `rcFile` is `null` (nushell, powershell): return manual instructions
3. Create parent directory if missing (important for Fish: `~/.config/fish/`)
4. Read existing content, then **drop any stale block of the opposite kind** — e.g. an `unset STARSHIP_CONFIG` guard left over from an earlier run where the shell wasn't selected — so a re-run can repair a polluted rc file
5. **Idempotency check**: if any of the lines about to be added (PATH, config, init) is already present, skip that line rather than duplicating it; if the whole block is already configured, skip
6. If the rc already has a Starship init line, insert the new lines just above it (joining an existing managed block when there is one); otherwise append a new block

Two further details:

- **PATH fix-up**: when Starship was installed via the official script and the binary landed in `~/.local/bin` (not on PATH in most environments), a PATH line in that shell's own syntax (`export PATH=...` for zsh/bash, `fish_add_path` for fish) is prepended before the init line — `getMissingStarshipPathDir()` is checked once after the install so the rc lines can repair PATH when the script install left the binary somewhere the shell won't look.
- **Order matters**: the PATH and `STARSHIP_CONFIG` lines must come before the init line, or `starship init` cannot resolve either the binary or its config.

`resetSharedShellConfig(shellId)` adds `unset STARSHIP_CONFIG` (fish:
`set -e STARSHIP_CONFIG`) above the init line so the shell falls back to the
shared file instead of inheriting a config leaked from a parent. It first removes
a per-shell block an earlier run wrote, carrying its PATH line over and keeping
the Starship init line, so an unselected shell still starts Starship with the
shared config. A shell whose own, hand-written line sets `STARSHIP_CONFIG`
cannot inherit a leaked value, so it is left alone apart from dropping a stale
unset guard that would cancel that export. `applyShellConfig` likewise removes stale unset guards, so re-running
the wizard can switch modes without losing shell startup wiring.

**Adopt mode** reorders the three states rather than adding a fourth surface. `applyShellConfig`
with `pointAtSharedConfig: true` still writes the `starship init` line, but omits the
`STARSHIP_CONFIG` export, so the shell falls back to the shared `~/.config/starship.toml` by
Starship's own default. The block is emitted under a distinct marker,
`# Added by ShellConfigurator (shared config)`, so a later non-adopt run can recognise and drop it;
a non-adopt run's per-shell `export` is likewise dropped when a shell flips to adopt, keeping
adopt and non-adopt mutually exclusive in both directions. In adopt mode no `STARSHIP_CONFIG` points at per-shell files,
because none exist.

## Installer Task System

**Files**: `src/services/installTasks.ts` (orchestration) + `src/services/installer.ts` (commands) + `src/screens/InstallingScreen.tsx` (rendering)

### Task Construction

`buildTaskList(state)` creates the task queue from wizard state:

| Task          | Condition                                                                              | Action                                                                                                                                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Starship      | Not `skipStarshipInstall`                                                              | Install if not already present                                                                                                                                                                                                        |
| Nerd Font     | `nerdFontToInstall.kind === 'install'` and not `container`                             | Download and install font (skipped in containers — fonts belong to the host terminal)                                                                                                                                                 |
| Terminal font | `nerdFontToInstall.kind === 'install'` and a terminal was detected and not `container` | Wire the font family into the terminal's config (`terminalFont.ts`)                                                                                                                                                                   |
| Shell(s)      | Selected shell not in `installedShells`                                                | Install via package manager; shells that cannot be installed automatically (`shellInstallSupported` = false: the `script` fallback or no package for that manager) are tagged "(manual)" in the plan so the user knows before the run |
| Set default   | `setDefaultShell` is set (and not `container`)                                         | Run `chsh -s <path>` (meaningless in a container, skipped)                                                                                                                                                                            |
| Config        | Always                                                                                 | Write per-shell configs, or keep/adopt the shared config                                                                                                                                                                              |
| RC files      | Always (marked skipped when `skipStarshipInstall`)                                     | One task per shell: init line + `STARSHIP_CONFIG` pin                                                                                                                                                                                 |
| Verify config | Not `skipStarshipInstall`                                                              | After the rc steps: run `starship print-config` against each written config                                                                                                                                                           |
| Unset guard   | Not `skipStarshipInstall`; an installed, unselected shell whose rc loads Starship      | After Verify: `resetSharedShellConfig` adds an `unset STARSHIP_CONFIG` guard (one task per shell)                                                                                                                                     |

The Config task writes _per-shell_ configs, one per selected shell, and the shared
`~/.config/starship.toml` is only snapshotted. In adopt mode the Config task instead either keeps
the existing shared config or writes the `--import-url` fetch, and the RC tasks run with
`pointAtSharedConfig` so the shells read that shared file with no `STARSHIP_CONFIG` export. The RC step is one task per shell so
a failure in one does not taint the others. After `Verify config` comes a final
pass that writes an `unset STARSHIP_CONFIG` guard into every installed shell
that wasn't selected and whose rc already runs `starship init`
(`resetSharedShellConfig`). Those shells are found at run time, so their tasks
join the list once the run starts. The guard
prevents a configured parent's per-shell config from leaking into that shell;
the existing Starship init line remains in place and uses the shared config.

Choosing "Continue without Starship" sets `skipStarshipInstall`, so the Starship, Verify config, and unset-guard tasks are omitted and each RC task is shown as skipped ("install Starship first") — writing `eval "$(starship init …)"` lines for a shell without Starship would error on every new shell.

Three failure nuances make the generated config honest:

- If the font install fails but the user opted into one, the Config task **re-generates the TOML with `hasNerdFont: false`** so the written file has no glyphs the terminal cannot render, and notes it. The Terminal-font task then skips itself (wiring the terminal at a font that is not there would be a lie).
- If no shell is selected, the Config task fails with a clear message ("No shells selected — nothing to configure").
- If the Config task fails for any reason, the RC tasks of the selected shells are **marked failed with the config error** instead of running: an `init` line pointing at a config that was never written would only produce a broken prompt.

After a fresh Starship install the version is recorded to the cache dir, and the
`Verify config` task runs `verifyStarshipConfig` (`installer.ts`) against every
config this run wrote, resolving a script-install bin dir when the bare binary is
not on the current PATH. `starship print-config` exits 0 even on a broken
config, so any warning it prints on stderr fails the task with that text instead
of a silent success. The doctor uses the same function.

### Task Lifecycle

Each task transitions through these statuses:

```
pending → running → done
                  → failed (with error message)
                  → skipped (e.g., Starship already installed)
```

Status is displayed with icons:

```
[✓] Starship                     (done, green)
[~] Nerd Font (JetBrains Mono)   (running, yellow)
[ ] Write config files          (pending, gray)
[✗] Install fish                 (failed, red)
    Error: apt-get not found       (error detail)
[–] Set zsh as default shell     (skipped, gray)
```

### Execution Flow

Orchestration lives in `src/services/installTasks.ts` as `runInstallTasks(state, deps, onUpdate, signal?)` — a dependency-injected service. The installer, generators, and detector functions are passed in as `InstallTaskDeps` (the real wiring is `DEFAULT_INSTALL_TASK_DEPS`); tests inject fakes. The function tracks an internal task list, reports every status change through `onUpdate(id, patch)`, and returns the final `InstallTask[]`.

`InstallingScreen` passes an `AbortController`'s signal as the fourth argument, and `runInstallTasks` hands it on to every install command. Pressing `c` (or Ctrl+C, which arrives as `SIGINT` while a child owns the terminal) aborts it: the command in flight is killed, and the next task finds the signal aborted, so every task that never ran is marked `failed` ("Cancelled") — never silently `done`.

`InstallingScreen` starts the run from a mount `useEffect`. Its cleanup aborts the controller, so when React StrictMode runs the effect twice the first run is cancelled before any step starts and the second one finishes:

```typescript
useEffect(() => {
  let unmounted = false;
  const controller = new AbortController();
  abortRef.current = controller;
  // ... runInstallTasks(state, DEFAULT_INSTALL_TASK_DEPS, updateTask, controller.signal) ...
  return () => {
    unmounted = true;
    controller.abort();
  };
}, []);
```

Every task runs through `runTask` in `installTasks.ts`, which wraps it in try-catch. Failures are recorded but do **not** halt the pipeline — remaining tasks still execute. The RC step is one task per shell, and the Config task collects per-shell write errors, so one shell's failure doesn't block the rest.

After all tasks complete, a 1200ms delay lets the user see the final state before auto-advancing to the Done screen. The final task list returned by `runInstallTasks` is passed to DoneScreen via `installResults` in `WizardState`, so DoneScreen can display actual success/failure status for each task.

### Command Execution

All install commands go through `runCommand` in `src/services/exec.ts` — an async `spawn`, never `spawnSync`. A blocking `spawnSync` call would freeze the whole Ink render loop and give no way to cancel. Because the child writes to the same TTY Ink draws on, the terminal is handed over for the child's lifetime:

- **tty suspension** (`services/tty.ts`): the UI renders nothing while a child owns the terminal (`sudo` prompts, `chsh`), and raw mode is switched off so password/confirmation input works. Screens subscribe and render `null` while suspended, so Ink's next frame can't paint over the prompt
- **cancellation**: the optional `AbortSignal` kills the child with `SIGTERM`, escalating to `SIGKILL` after `KILL_ESCALATION_DELAY_MS` (5s) if it is still running; the Install screen's signal reaches it through `runInstallTasks`
- **failure modes**: `runCommand` checks three in order — the spawn `'error'` event, an `'exit'` with a signal, then a non-zero exit status. It settles on `'exit'`, not `'close'`: a child that backgrounds a grandchild keeps its stdio open, so `'close'` never fires even though the process has ended. Each failure path produces a distinct, actionable error message.

`installer.ts` (Starship/shell installs, `chsh`) composes commands and delegates to `runCommand`; fonts never go through the shell — `installNerdFont` downloads with `fetch` and hands the archive to a worker (below).

### Verified Font Downloads & Sandboxed Extraction

`installNerdFont` treats a downloaded archive as hostile input until proven otherwise:

1. **Download guards**: the request carries an `AbortSignal.timeout` (`FONT_DOWNLOAD_TIMEOUT_MS`), so a hung connection can't wedge the install chain, and the archive is refused when the declared `content-length` or the received buffer exceeds `MAX_FONT_ARCHIVE_BYTES`.
2. **Checksum verification**: before extraction the buffer's SHA-256 is computed (`node:crypto`) and compared with the `sha256:` digest GitHub publishes in the release asset metadata (`GET /repos/ryanoasis/nerd-fonts/releases/latest`, matched by `zipName`). The lookup also has its own `AbortSignal.timeout`. The check fails closed: a mismatched archive, a release without a digest for the asset, or a failed lookup with nothing cached all refuse to install with distinct errors. A verified archive is cached after install and reused, without downloading, when its digest still matches the latest release or the lookup fails.
3. **Worker-isolated extraction** (`src/services/fontExtractor.ts`): `extractFontFiles()` decompresses in an `eval`-script `Worker` (CommonJS `require` of the resolved fflate path, archive and path passed through `workerData`), so malformed input can only crash the throwaway worker, never the wizard. It refuses an archive whose entries expand past a per-entry or total size cap. The worker filters entries to font files and flattens them to basenames — deliberately structured-cloned back as `{ name, bytes }` while the _writes_ stay on the main thread, keeping path handling and `fs.writeFileSync` in one auditable place. A ~60s timeout terminates a stuck worker.

### Platform-Aware Font Installation

`installNerdFont` uses platform detection for the fonts directory:

- **macOS** (`process.platform === 'darwin'`): `~/Library/Fonts` — macOS auto-detects fonts here, so `fc-cache` is skipped
- **Linux**: `~/.local/share/fonts` — runs `fc-cache -f` after extraction (non-fatal when `fc-cache` is missing)

If extraction succeeds but yields no font files, the install fails loudly ("No font files found") rather than silently writing nothing.

## Detection System

**File**: `src/services/detector.ts`

### Package Manager Detection

`detectPackageManagerAsync()` runs a prioritized detection chain. Binary checks use `sh -c 'command -v "$1"'` (a POSIX shell builtin) rather than `which`, which is absent on minimal/Fedora/Alpine images. The command name is passed as `$1`, never spliced into the script text, so a crafted name cannot become shell syntax:

```
1. command -v brew     → 'brew'      (macOS / Linuxbrew)
2. command -v pacman   → 'pacman'    (Arch-based; a /usr/games/pacman game binary is ignored)
3. os-release ID, then ID_LIKE → match, used only when that manager's binary exists:
   ├── ubuntu, debian, linuxmint, pop, elementary   → 'apt'
   ├── fedora, rhel, centos, rocky, almalinux       → 'dnf'
   ├── arch, manjaro, endeavouros, cachyos, garuda  → 'pacman'
   └── alpine                                       → 'apk'
4. command -v apt-get  → 'apt'       (fallback binary check)
5. command -v dnf      → 'dnf'       (fallback binary check)
6. command -v apk      → 'apk'       (fallback binary check — Alpine/Alpine-based containers)
7. fallback            → 'script'    (curl install script)
```

**Why command checks come first**: Homebrew can be installed on Linux, and `command -v brew` is faster than reading `/etc/os-release`. Pacman is checked early because Arch-based distros don't always have a predictable OS ID.

**Why binary fallback exists (steps 4-6)**: Some minimal containers or custom distros have no `/etc/os-release` (or an ID that maps to nothing) but do have `apt-get`, `dnf`, or `apk` in PATH. The os-release match in step 3 only breaks a tie between managers that are actually present — CentOS 7, for instance, has `yum`, not `dnf`.

### OS Release Parsing

`readOsReleaseIdsAsync()` reads `/etc/os-release` (falling back to `/usr/lib/os-release`) and returns the `ID` field followed by the `ID_LIKE` parents, so a derivative (e.g. `kali`, `debian`) maps to its parent's package manager:

```
ID=ubuntu     → 'ubuntu'
ID="rocky"    → 'rocky'
ID='arch'     → 'arch'
```

Handles both quoted and unquoted values.

### Shell Detection

`detectInstalledShellsAsync()` checks the binary of each entry in the `SHELLS` table — in parallel via `Promise.all`, and using the binary name from the definition rather than the id. The binary names checked today are:

| Shell ID   | Binary Checked |
| ---------- | -------------- |
| bash       | `bash`         |
| zsh        | `zsh`          |
| fish       | `fish`         |
| nushell    | `nu`           |
| powershell | `pwsh`         |

Returns an array of `ShellId` values for shells found in PATH.

### Starship Detection

`isStarshipInstalledAsync()` runs `starship -V`:

- Success: returns `{ installed: true, version: "starship 1.x.x" }` (`-V` prints only the version line)
- Failure: returns `{ installed: false }`

Used by both WelcomeScreen (to show status) and InstallingScreen (to skip installation).

When the Starship task performs a fresh install, the reported version is recorded
to the cache dir (`recordStarshipVersion`). The doctor reads it back
(`cachedStarshipVersion`) to flag version drift when a later package-manager
upgrade moves starship under the tool's nose.

### Terminal & Container Detection

`detectTerminalAsync()` identifies the terminal emulator from the environment
markers each one sets: `KITTY_WINDOW_ID` or `TERM=xterm-kitty` (kitty),
`GHOSTTY_RESOURCES_DIR` (ghostty), `WEZTERM_PANE` (wezterm),
`ALACRITTY_WINDOW_ID`/`ALACRITTY_SOCKET` (alacritty), and a `foot` `$TERM`
(foot), with a matching `$TERM_PROGRAM` also accepted for the first four. A
subsequent task can then wire the installed Nerd Font into its config.
`detectContainerAsync()` treats the run as a sandbox when any of `CODESPACES`,
`REMOTE_CONTAINERS`, `DEVCONTAINER`, `CI`, `KUBERNETES_SERVICE_HOST`, or
`container` is set (and not empty, `false`, `0`, or `no`), or when a marker file
container runtimes drop exists (`/run/.containerenv`, `/.dockerenv`,
`/run/systemd/container`). In a sandbox the font and `chsh` tasks are dropped
because fonts are per-host and `chsh` is meaningless there.

### Async-Only Detection

Every detection function is async and there are no sync counterparts — they run during the Ink render loop and must not block it. They use `promisify(execFile)` rather than `execFileSync`:

- **`detectPackageManagerAsync`**: Parallelizes independent checks — `brew` + `pacman` run together, then the os-release read + `apt-get` + `dnf` + `apk` together — while preserving priority order
- **`detectInstalledShellsAsync`**: Runs all shell checks in parallel via `Promise.all` (biggest performance win — wall-clock time drops from 5 sequential forks to 1 parallel batch)
- **`isStarshipInstalledAsync`**: Single async `execFile` call

WelcomeScreen and ShellScreen await them in `useEffect` with a `cancelled` guard; InstallingScreen goes through the `installTasks` service, which uses `isStarshipInstalledAsync` for the same reason.

### Cross-Distro Smoke Testing

The `.github/workflows/ci.yml` `distro-smoke` job runs `scripts/dockerSmoke.mjs` — `detectPackageManagerAsync`, `detectInstalledShellsAsync`, `isStarshipInstalledAsync`, `generateToml` (parsed as TOML for every preset), `applyShellConfig` idempotency, the Nushell setup command resolving to its per-shell config, and `applyShellConfig`/`resetSharedShellConfig` staying mutually exclusive across re-runs (stale unset guards dropped, polluted rc files repaired), a backup/restore round trip of the per-shell and shared configs, and a real script install of Starship — all against a scratch `HOME` inside Ubuntu, Debian, Fedora, Arch, and Alpine containers, plus synthetic `brew` and `script`-only entries. This exercises the detection chain against real `/etc/os-release` and package-manager layouts without a VM matrix. It caught the `which`-absence issue on Fedora that led to the `command -v` change above. Each matrix entry then runs its `wizard-check` command against a scratch `HOME`: every entry runs `headlessGenerateSmoke.mjs`, which presses the real entrypoint through `generate` (stdout + `-o`/`--export`) and parses the result, then runs `debug-info` (Markdown and `--json`) against the real detection, `/etc/os-release` and doctor, asserting the home directory never appears, loads the real `completions bash` script into bash to check it completes a subcommand and a flag value, and parses the `--list-presets --json`, `--list-fonts` and `apply --dry-run --json` output, checking that its diff of `.bashrc` adds the init line and that the dry run left `.bashrc` alone; every entry except `brew` also runs `headlessApplySmoke.mjs` (a real `apply --shells bash` that must pass `Verify config` and write `WHAT-CHANGED.md`, then a real `uninstall --yes` checked for a clean rc, a backed-up config and a summary left in place, a second uninstall that removes nothing, a `rollback --list`, a `rollback --yes` that must bring the rc block and config back, and a second `rollback --yes` that must undo the apply itself, summary included); and only the `script` entry runs `scripts/ci/wizardSmoke.mjs`, which drives the _real_ `App` from `dist/` through the full install flow. Containers that ship an old Node get a pinned Node 24 tarball from `scripts/ci/distroSetup.sh` first, so every container meets the supported engine floor.

The `macos-smoke` job in `ci.yml` (`Distro smoke (macos)`) builds `dist/` and runs a headless smoke (`scripts/ci/macosSmoke.mjs`) against a scratch `HOME`: it drives the real entrypoint through `generate`, `apply --dry-run --adopt`, and a real headless `apply` that installs Starship with brew and verifies the config, so the darwin-only paths (brew detection, `~/Library/Fonts`) are exercised. Config and rc writes stay in the scratch `HOME`.

## Error Handling Strategy

The app handles errors at different levels:

| Layer                                      | Strategy                                                             |
| ------------------------------------------ | -------------------------------------------------------------------- |
| Detection (`detector.ts`)                  | Swallow errors, return safe defaults (`false`, `null`, empty arrays) |
| Installation (`installer.ts`)              | Throw on failure — caught by `runTask`                               |
| Task runner (`runTask`, `installTasks.ts`) | Catch per-task, record error, continue remaining tasks               |
| Config writing (`shellRc.ts`)              | Throw on failure — caught by `runTask`                               |

This means a font download failure won't prevent config file writing, and a missing `chsh` binary won't block RC file updates.
